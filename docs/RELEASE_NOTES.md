## 1. What this release is

A governed workflow-automation platform. A natural-language request or a
versioned YAML workflow becomes a validated DAG; every node passes a
deterministic policy gate; risky nodes wait for a human quorum; work is
dispatched to workers over Redis Streams; every run is hash-chain audited and
can be replayed from its pinned version. The AI is an optional planner and never
an authority for authorization, risk, execution or audit.

**Delivered capability, by requirement area:**

| Area | What ships | Requirements |
|---|---|---|
| Authoring | typed YAML DSL (5 node types, 3 triggers), 5-stage validator with `stage:line:column`, immutable versions | FR-03, FR-04, FR-05 |
| Planning | deterministic offline planner (9 intents), clarification response, typed optional LLM adapter | FR-06 |
| Safety | policy service (`ALLOW`/`NEED_APPROVAL`/`DENY` + score/reasons/quorum/version), readable explanations, inert dry run | FR-07 |
| Governance | JWT + PBKDF2 auth, frozen RBAC matrix, approval quorum/expiry | FR-01, FR-02, FR-08 |
| Execution | DAG scheduler (concurrency, timeout, retry, propagation, compensation), shell/approval workers, GUI/custom stubs | FR-10, FR-11 |
| Messaging | frozen event contract, consumer groups, idempotency, backoff, DLQ, manual/file.arrived/schedule triggers | FR-09 |
| Evidence | append-only hash-chain audit, query/timeline/verify endpoints, run metrics | FR-12, FR-16 |
| Recovery | replay from the pinned version with normalized comparison, backup/restore, tested migration upgrade | FR-13 |
| Memory | consent-gated, PII-scrubbed shared memory; quarantine/reputation-gated reuse; erasure | FR-14, FR-15 |
| Sandbox | frozen `sandbox-v1` contract, namespace isolation + audit-hook fallback, plugin manifest validation | NFR security |
| Client | Tkinter workbench (workflow, runs, approvals, audit) | FR-08, NFR usability |
| Ops | one compose stack (+ a production file that refuses default secrets), structured redacted logs, rate limits | NFR deployability |

## 4. Upgrade / migration notes

- Schema migrations `001`–`007` apply automatically and are checksum-tracked;
  a drifted or hand-edited migration is reported, not silently re-run.
  Upgrading from a 4-migration database was tested (`docs/DEPLOYMENT.md` §3).
- `compose.yml` uses a **named volume** for `/data`; the pre-fix behaviour
  (SQLite inside the container layer) lost state on `--force-recreate`. If you
  deployed before this tag, move the file out of the container before upgrading.
- Migrations are forward-only; take a backup first
  (`python scripts/backup.py`), which also verifies the snapshot manifest and
  the audit chain.
- `compose.prod.yml` refuses to start while `SECRET_KEY`/admin credentials are
  still at their development defaults, and publishes only `127.0.0.1:8000`.

## 5. Known limitations and deferred features

The full list is [`docs/LIMITATIONS.md`](LIMITATIONS.md) (deliberate scope
boundaries, architectural limits, testing gaps, privacy, platform, `STRETCH`
items). The ones a user will meet first:

- `shell` nodes are **record-only** in the worker; the sandboxed `custom`/plugin
  path is where untrusted code really executes;
- `gui_click`/`gui_type` are explicit non-production **stubs** — no VLM automation;
- the planner covers **9 intents**; unusual requests get a clarification, not a plan;
- SQLite is a single writer and rate limiting is **per process**;
- the sandbox is namespace-level isolation, not a hardened container runtime;
- the shared memory's embeddings are hashing-based, not semantic.

- No usability result (the study has not run).
- No provider-verified LLM behaviour (the adapter is off by default and tested
  against a fake client).
- No external audit anchoring, no chaos suite, no independent third-party review,
  and deployment verified on a single host — each is stated as exposure in
  `docs/RISK_REGISTER.md` §4.
